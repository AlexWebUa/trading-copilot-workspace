# Critical Review — Trading Co-Pilot
_2026-06-10 · Reviewed: PLAN.md, PROGRESS.md, detectors, backtest engine, data layer, LLM layer, tests_

## Verdict

The architecture (pure detectors + compact JSON + LLM reasoning) is sound and the engineering discipline is above average. But the project currently **cannot be trusted for live decisions or backtest conclusions**, for three reasons:

1. **Live analysis runs on the forming candle** — every detector treats Binance's incomplete last kline as closed.
2. **The backtest engine has look-ahead leaks** (LTF entry timing, forming HTF bars) — reported winrates are inflated.
3. **The May 2026 P0 detector rewrites were never done** — liquidity, sponsored_candle, CD, and compression still contain the exact bugs the audit documented, and the tests that "pass" are the vacuous schema tests the project's own rules forbid.

Nothing below requires new features. It requires finishing what the May course-correction already decided, plus deleting code that open-source libraries do better.

---

## A. Correctness bugs (reliability)

### A1. Forming-bar contamination — P0, live analysis
Binance `/klines` returns the current **incomplete** candle as the last row. `normalize_binance()` keeps it; no code anywhere drops it (`grep` for forming/iloc[:-1] confirms). Consequences:

- Every MCP/REPL analysis treats a candle that can still repaint as confirmed. A "BOS by candle close" or "sweep with close-back" detected on the forming bar can vanish minutes later.
- This silently violates the protocol's hardest rule: *entry only on candle CLOSE*.

**Fix:** in `normalize_binance`, drop the last row when its `close_time > now` (the field is already in the response and currently discarded). Add a `include_forming=False` default. One-line class of bug, system-wide payoff.

### A2. Backtest LTF entry look-ahead — P0, inflates results
`_find_ltf_idx()` seeds the LTF scan at the first LTF bar after the signal bar's **open** timestamp. But the signal is only knowable at the signal bar's **close**. On a 1h signal with 5m entry TF, the engine can "enter" at 12:05 on a signal that didn't exist until 13:00 — filling at prices from the past. Every LTF-confirmed backtest result is optimistic by construction.

**Fix:** seed the cursor at `signal_ts + tf_duration` (signal bar close), not `> signal_ts`.

### A3. Backtest HTF condition look-ahead — P0
`_evaluate_htf_conditions` slices `htf_df[htf_df.index <= current_bar_ts]`. Binance indexes bars by open time, so the slice includes the **forming HTF bar** whose high/low/close contain up to several hours of future data (1h signal bar inside a 4h bar that closes 3h later). HTF structure conditions are evaluated on data the trader couldn't have had.

**Fix:** include only HTF bars whose *close time* ≤ current bar's close time: `htf_df.index + htf_duration <= current_bar_ts + tf_duration`.

Related bugs in the same function:
- HTF cache key `(htf_tf, detector, htf_bar_idx)` ignores `kwargs` — two conditions on the same detector/TF with different params silently collide.
- HTF data is fetched as "most recent N bars" regardless of backtest `start`/`end`. A backtest on an old range gets HTF data that may not cover it → conditions return False → zero signals, with no warning.

### A4. P0 detector rewrites marked "pending" since May are still pending
PLAN.md's own audit table is accurate — the code matches the *broken* descriptions:

| Detector | Audit said | Code today |
|---|---|---|
| `detect_liquidity` | "`is_swept` incorrect (trades-above ≠ sweep)" | Still `swept = (highs[i+1:] > highs[i]).any()` — any later trade above marks it swept; the close-back test exists only in `_find_sweeps`, which scans just the last 30 bars |
| `detect_sponsored_candle` | "should be sweep_candle = OB" | Still searches a 5-bar pre-window for a sweep before a separately-detected OB |
| `detect_cumulative_delta` | "divergence and sweep thresholds flawed" | Divergence compares only the **current bar** vs. bars at lag 2–10 (no swing-to-swing logic; fires only if the latest bar is the extreme). Sweep detection never checks close-back, and `wick_threshold=0.002` of bar range means *any* bar with a visible wick that exceeds the 4-bar high counts as a "sweep" — `confirmed_manipulation` is near-noise |
| `detect_compression` | "volatility squeeze ≠ LRLR" | Still strictly-narrowing consecutive ranges. Also a terminology error: in SMC, **LRLR = Low Resistance Liquidity Run**, not "Lower Range Lower Range" — the detector measures a different concept than the KB term it claims to implement |

These detectors feed `prompts.py`'s strongest language ("HIGHEST-QUALITY reversal signal — institutional print" for `confirmed_manipulation=true`). Right now the prompt instructs Claude to upgrade confidence on a near-random signal. **Until A4 is fixed, the orderflow section of every report is actively harmful.**

### A5. The tests that "pass" prove little
281/281 pass, but e.g. `test_detectors_liquidity.py` is exactly the pattern the project's own Working Rules forbid:

```python
assert total >= 0  # can be 0 ... at minimum no crash
```

This is vacuously true. The liquidity, CD, and compression test files predate the test-standard reform and were never upgraded — which is precisely why the broken detectors in A4 show green. The test count is providing false confidence; treat "281 passing" as unverified until each flagged detector has positive/negative/edge fixtures with asserted values.

### A6. Smaller correctness issues
- **`tools_confirmed` is wrong in backtest records** — `engine.py` sets `tools_confirmed=list(signal_cache.keys())`, i.e., every detector the rule *evaluated*, identical for every trade of the same rule. The Phase-6 "tool-effectiveness Δwinrate ranking" is therefore degenerate on backtest data: within a rule it cannot vary, so the ranking measures rule identity, not tool contribution.
- **Fee model counts one side.** `_finalize_trade` deducts `entry_price * fee_bps` once; the docs define `fee_bps` "per side". Real round-trip cost is ~2× what's deducted (plus funding on perps — not modeled at all). Backtest expectancy is overstated.
- **`agent.py` keys tool results by name only** (`all_tool_results[block.name] = result`) — a multi-TF analysis calling `detect_market_structure` on D1/H4/H1 keeps only the last TF. The state-diff feature ("Previous Analysis Context") is built on corrupted state. Key by `(name, symbol, tf)`.
- **`simulate._resolve_limit_level` picks `fvgs[0]`/`obs[0]` without checking direction** — a long can get a limit level from a bearish FVG.
- **`fetch_ohlcv_with_delta` bypasses both the cache and the injected `DataSource`** — every CD call is a live API hit, and the backtest delta path ignores mock sources (tests silently exercise the fallback).
- **Inconsistent ATR definitions:** `liquidity.py`/`compression.py` use rolling mean of high−low; `simulate.py` uses true range. Same word, different numbers. The protocol's "rolling per-bar atr_arr" rule is also not followed in `liquidity.py` (single scalar ATR for the whole window).
- `detect_liquidity`: schema default `lookback=150` vs. function default `80`; `_count_touches` has dead `idx`/`is_high` params; EQH classification counts *any* bar within tolerance across the window (two unrelated swings months apart become "EQH"); sweeps sorted by string timestamp, violating the project's own "integer idx" rule.
- `agent.py` appends the assistant turn twice (full `resp.content`, then `final_text` again) — conversation history sent to the API on follow-ups contains duplicates.

## B. Replace with open source instead of fixing

### B1. Detector math → depend on `smartmoneyconcepts` directly (highest-value change)
PLAN.md declares the `smartmoneyconcepts` library "algorithmic ground truth" — yet it is **not in pyproject.toml**, and every detector is a hand-rolled reimplementation "per smc.py". This is the root cause of the May incident: reimplementations drift, and bugs surfaced only via manual chart comparison months later.

Recommendation: add it as a dependency and make `swing_highs_lows`, `bos_choch`, `ob`, `fvg`, and `liquidity` thin wrappers: call the library, convert its DataFrame output to your compact JSON (fill_state enums, ATR distances, ISO timestamps). You keep the LLM-facing contract; you delete the logic that keeps breaking. Detectors with no library equivalent (sponsored candle, killzones, multi-TF alignment, composites) stay custom — that's where your actual edge/KB-specificity lives. This also resolves A4 for liquidity semi-automatically.

### B2. Backtest fills/metrics → `vectorbt` (or `backtesting.py`)
`engine.py` is 941 lines of hand-rolled state machine, and Section A shows it has the classic hand-rolled-backtester bugs (look-ahead, one-sided fees, no slippage, no funding). Execution simulation is a solved problem. Keep `SetupRule` + detectors as the **signal layer** (they're the differentiated part), emit entry/SL/TP arrays, and let vectorbt handle fills, partial exits, fees both sides, slippage, and the stats (Sharpe, drawdown, trade tables). Your `_IN_TRADE_P2` / `sl_after_tp1` / `max_bars_open` logic all map to vectorbt order/exit primitives. The multi-TF condition gating stays yours but becomes a boolean mask, which is far easier to audit for look-ahead than a 5-state machine.

If a full migration is too disruptive, the minimum is: fix A2/A3, add two-sided fees + a slippage parameter + funding-rate approximation, and add an automated look-ahead test (run the same rule on `df` vs. `df` with the last K bars perturbed; signals before the perturbation must be identical).

### B3. Performance reporting → `quantstats` (already planned, do it instead of growing `stats/`)
P2b is the right call — promote it. Don't add more metrics to `aggregator.py`; keep only the KB-specific groupings (setup/session/killzone/tool) there. Note the tool ranking is unusable until A6's `tools_confirmed` bug is fixed.

### B4. Keep custom (correctly rejected alternatives)
SQLite-WAL journal, parquet cache, MCP server on `ToolRegistry`, KB keyword selector (embeddings still premature), triangular VP approximation (honest about its limits), klines-based CD (right call vs. aggTrades pagination — but document that taker-buy proxy ≠ true bid/ask delta). These are appropriately small and not worth external dependencies.

## C. Profitability — the missing evidence loop

The system has never demonstrated edge; it has accumulated machinery for demonstrating edge. Critically:

1. **Every existing backtest number is invalid** (A2/A3/A6 fees). First action after fixes: re-run all rules, walk-forward, with two-sided fees + slippage. Expect materially worse numbers; that's the real baseline.
2. **Single IS/OOS split is weak validation.** With the small trade counts these rules produce, one split is noise. Use rolling walk-forward (trivial in vectorbt) and report binomial confidence intervals on winrate — a 55% winrate over 40 trades is statistically indistinguishable from 50%. Display CI in `stats` output so the LLM and the trader stop over-reading small samples.
3. **The LLM layer has no eval harness.** PLAN.md's verification check #3 ("every price in the report appears in a tool result") is the architecture's core promise, but it's manual. You already write trace JSONL per tool call — add an automated post-analysis check that extracts numbers from the report and asserts each appears in the trace. Fail loudly. This converts your P0-bug definition into a test.
4. **Prompt drift vs. protocol.** The May 30 protocol mandates the HTF-POI hard gate, the `## HTF POI` section, conflict-resolution hierarchy, and the no-BE rule. `prompts.py` contains none of these (P1 "workflow revision" is pending). The deployed prompt also tells Claude to treat `confirmed_manipulation` as the highest-quality signal (see A4). Prompts must not lead detector quality.
5. **Sequencing discipline.** The roadmap's P3 dashboard, P4 screenshot analysis, and P5 instruments are all premature. The honest critical path is: **A1 → A2/A3 → A4 (via B1) → real tests for flagged detectors → re-baseline backtests (B2/fees) → P1 prompt revision → only then features.** Each later phase consumes data produced by the earlier ones; right now that data is contaminated at the source.
